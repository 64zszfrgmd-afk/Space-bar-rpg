# Production 0.21.3: подготовка, без merge

Владелец подтвердил 14 ноября 2026 проверку опубликованной тестовой 0.21.3 на физическом iPhone: пять видов переключаются, путешествия работают, внешность сохраняется после перехода и перезагрузки Safari. Проверенный тестовый код — `cc18f552bae5f528ed2dda4dbbb24e7b05c18a66`. Подготовка релиза не меняет этот код. Проверка production после её публикации ещё обязательна; релиз не объявляется завершённым заранее.

## Наследование и порядок объединения

Состояние до подготовки: main `ffa62be7404559a51157a86efbc3785b7dece82a`, версия 0.21.0. Все три PR открыты, draft, mergeable=true, mergeable_state=clean, base=main:

`git merge-base --is-ancestor` подтверждает main → head #7 → head #8 → head #9. Использовать **один merge commit PR #9 в main**, только после отдельного разрешения владельца. Не объединять #7/#8 отдельно, не делать cherry-pick, squash или rebase этой цепочки. Старые PR, ветки и тестовые файлы сохраняются. После единого merge GitHub может сам отметить вложенные PR как включённые в main; вручную их не закрывать и ветки не удалять.

1. Убедиться, что main осталась `ffa62be`, а окончательный head #9 соответствует проверенному CI. Если main изменится — заново собрать и проверить merge-result, обновить снимок опубликованных файлов.
2. В Settings → Rules → Rulesets / Branches включить для main обязательные PR и проверки: `production candidate and preservation`, `build (chromium)`, `build (webkit)`, `permanent recovery point`, `release-ready`; требовать актуальную ветку. Во время аудита main **не защищена**, rulesets пусты. Workflow запрещает deploy при неуспешных/пропущенных зависимостях, но сам по себе не запрещает владельцу нажать merge. Без настройки защиты проверки нельзя называть принудительно обязательными для merge.
3. После всех зелёных проверок и отдельного разрешения выполнить только **Create a merge commit** для #9. Не включать auto-merge заранее.
4. Main push заново запускает полные проверки обоих браузеров. Только `release-ready=success` разрешает публикацию составного сайта. Production проверяет актуальный main и все старые live-хеши непосредственно перед deploy.
5. Проверить production HTTPS и iPhone по инструкции ниже. Только после подтверждения основной версии объявить релиз завершённым.

## Release notes

- Исправления маршрутов и доступа из 0.21.1, восстановление ранее открытых доков, понятные причины отказа, диагностика и реальные touch-сценарии.
- Пять различных моделей из 0.21.2; корректная примерка, камера и мобильные кнопки.
- Объёмные Орбион и Лентокрыл из 0.21.3. Замена модели подтверждается реальными пикселями основного framebuffer, при ошибке возвращается прежняя модель и состояние. Журнал выбора/отрисовки/ошибок помогает проверке iPhone.
- Сохранены девять локаций, 23 NPC, задания, отношения, напитки, экономика, сиденья, танцы и ритм-игра.
- Production `/Space-bar-rpg/`, ключ `spacebar-restored-v020`, схема 2. Тестовые сохранения не импортируются в основную игру. Legacy `spacebar-v1` остаётся источником fallback; исходная резервная копия не перезаписывается.
- Production-пакет сохраняет **227 тестовых файлов** трёх версий побайтно и прежние root assets для кешированного HTML. Общий baseline — 233 файла с SHA-256.

## Проверки и ограничения

`npm ci`, `npm test` (54 Vitest + 8 Node), полная `npm run test:browser` в Chromium и WebKit на фактически составленном production-пакете; дополнительно `npm run test:production`: сохранения 0.20.0, 0.21.0, 0.21.2, 0.21.3, смена вида, путешествие, reload, настоящий откат на опубликованный бинарный 0.21.0 и повторное обновление в том же origin/localStorage. Проверяются неизменность старых backup/test namespace и прогресс. Новый сценарий использует только настоящие кнопки игры; тестовые mutator API отсутствуют в production.

Игровой код не менялся при подготовке: `src/` и конфигурация Vite остаются как в подтверждённой владельцем версии. Полный браузерный прогон проверяет 9 сцен, 23 NPC и 5 видов, отрицательные GPU-сценарии и снимки с одинаковой камерой. Результаты окончательного CI находятся в PR; отсутствие/пропуск/отмена любой обязательной работы означает «не готово». Linux WebKit не заменяет production-проверку физического iPhone.

Неполный/повреждённый неизвестный исходный архив 0.20 не выдаётся за проверенный: проверяются доступные совместимые сохранения восстановленной 0.20 R2. Safari Private Browsing и очистка данных сайта не гарантируют долговременное хранение; релиз не меняет настройки браузера и не очищает данные.

## Проверка основной игры на iPhone после разрешённой публикации

1. До публикации в **основной игре** экспортировать прогресс: меню → «Резервная копия прогресса», сохранить JSON в заметки. Не очищать данные Safari.
2. После успешного production workflow открыть обычный Safari в прежнем профиле: https://64zszfrgmd-afk.github.io/Space-bar-rpg/ . Тестовый адрес не переносит свой отдельный прогресс в production.
3. Перезагрузить страницу. Проверить HUD/диагностику: 0.21.3, origin/path основной игры, прежние кредиты, задания, пропуск и отношения.
4. В третьем лице выбрать все пять видов, особенно Орбиона/Лентокрыла, закрыть меню, пройтись, потанцевать, сесть/встать.
5. С открытыми доками перейти в другой бар. Перезагрузить Safari и проверить вид, место и прогресс. Не начинать новую игру.
6. Проверить доступность старых `/test/0.21.1/`, `/test/0.21.2/`, `/test/0.21.3/`; они должны оставаться прежними.
7. При проблеме сохранить диагностический отчёт и экспорт прогресса, сообщить результат. Не удалять сохранения. Применять [план отката](ROLLBACK-0213.md) только по отдельному решению владельца.
